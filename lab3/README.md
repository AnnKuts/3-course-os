# Лабораторна робота №3: Алгоритми заміщення сторінок
## Operating Systems Lab 3 — Page Replacement Algorithms (Variant 3: Random + WSClock)

Цей проект реалізує дискретно-подійну симуляцію системи підкачування віртуальної пам'яті (demand paging) на базі TypeScript (Node.js).

Проект виконано відповідно до методичних вказівок кафедри, першоджерела лекцій та усних роз'яснень викладача (Варіант 3: **Random + WSClock**).

---

## 1. Архітектура та розмежування Апаратури (MMU) і Ядра (Kernel)

Система чітко розмежовує апаратні та програмні рівні відповідно до моделі сучасної ОС:

```
+-------------------------------------------------------------+
|                      Процес (Process)                       |
|  - Власний віртуальний адресний простір                     |
|  - 1D Таблиця сторінок (PageTable: PTE[])                   |
|  - Робочий набір (WorkingSet, 90% локальність, 10% рандом)  |
+-------------------------------------------------------------+
                              |
                     Звернення до пам'яті
                              v
+-------------------------------------------------------------+
|                       MMU (Апаратура)                       |
|  - Перевіряє тільки PTE: P, R, M, PPN                      |
|  - Якщо P = 0 -> генерує переривання (Page Fault)           |
|  - Якщо P = 1 -> встановлює R = 1 (та M = 1 для запису)     |
|  - СУВОРА ВИМОГА: MMU НЕ знає дескрипторів фіз. фреймів     |
|    і НЕ оновлює часових міток!                              |
+-------------------------------------------------------------+
                              | (Page Fault)
                              v
+-------------------------------------------------------------+
|                        Ядро (Kernel)                        |
|  - Керує пулом фізичних фреймів (PhysicalPage[])            |
|  - Стратегія витіснення (RandomReplacement / WSClock)       |
|  - Backing Store (файлова система підкачування / swap)      |
|  - При витісненні: скидання мапінгу PTE, запис брудних (M=1)|
|  - При завантаженні: прив'язка до фрейму, оновлення PTE     |
|  - Встановлює lastAccessTime у дескрипторі PhysicalPage     |
+-------------------------------------------------------------+
```

## 2. Структури даних та критичні вимоги викладача

### PTE (Page Table Entry) — `src/pte.ts`
Запис таблиці сторінок моделює апаратну комірку пам'яті процесора і містить **ВИКЛЮЧНО 4 поля**:
- `P: boolean` — біт присутності (Presence bit).
- `R: boolean` — біт звернення (Reference bit), встановлюється MMU при читанні/запису.
- `M: boolean` — біт модифікації (Modification/Dirty bit), встановлюється MMU при запису.
- `PPN: number` — номер фізичного фрейму (Physical Page Number).

> **КРИТИЧНА ВИМОГА ВИКЛАДАЧА:**
> У PTE категорично заборонено додавати будь-які атрибути на зразок `lastUsed`, `lastAccessTime`, лічильники чи метадані алгоритмів витіснення. Формат таблиці сторінок фіксований апаратурою процесора.

### Дескриптор фізичного фрейму — `src/physicalPage.ts`
Структура даних операційної системи для управління RAM:
- `frameId: number` — індекс фізичного фрейму (0 .. N-1).
- `busy: boolean` — прапорець зайнятості фрейму.
- `mappedPTE: PTE | null` — зворотне посилання на відповідний рядок таблиці сторінок процесу.
- `ownerPid: number | null` — ідентифікатор процесу-власника.
- `virtualPageNumber: number | null` — номер віртуальної сторінки процесу.
- `lastAccessTime: number` — логічний час останнього звернення, який використовується алгоритмом WSClock.
  - Ініціалізується Ядром при завантаженні сторінки у фрейм.
  - Оновлюється WSClock, коли стрілка бачить `R = 1` та скидає його в 0.
  - **MMU ніколи не модифікує це поле!**

### Backing Store (Сховище підкачування) — `src/backingStore.ts`
Відстежує віртуальні сторінки, скинуті на диск при витісненні:
- Дозволяє розрізняти первинне завантаження сторінки (`firstTimeLoads`) від повторного читання з диска (`backingStoreReloads`).
- При витісненні брудної сторінки (`M = 1`) викликається `savePage(pid, vp)` та інкрементується лічильник операцій запису на диск (`dirtyWriteBacks`).

## 3. Алгоритми витіснення сторінок (Паттерн Strategy)

### Algorithm A: Random (`src/randomReplacement.ts`)
- Обирає рівномірно-випадковий зайнятий фізичний фрейм.
- Ігнорує історію використання сторінок і біти звернення.
- Використовує окремий генератор `SeededRNG` для повної детермінованості.

### Algorithm B: WSClock (`src/wsclockReplacement.ts`)
Реалізує кругову стрілку годинника за списком зайнятих фізичних фреймів:
- Конфігурований параметр `TAU` (часове вікно робочого набору в одиницях логічних звернень до пам'яті).
- При огляді фрейму:
  - **Якщо `R = 1`**: скидає `R = 0`, оновлює `PhysicalPage.lastAccessTime = currentTime`, просуває стрілку далі.
  - **Якщо `R = 0`**: обчислює `age = currentTime - frame.lastAccessTime`.
    - Якщо `age > TAU`: сторінка знаходиться поза робочим набором!
      - Якщо `M = 0` (чиста) -> негайно обирається як жертва на витіснення!
      - Якщо `M = 1` (брудна) -> запам'ятовується як кандидат (потрібен запис на диск).
    - Якщо `age <= TAU`: сторінка активна в поточному робочому наборі -> пропускається.
- **Гарантія зупинки та детермінований фолбек (за роз'ясненнями лектора):**
  1. Якщо чистих не знайдено, береться найстаріший брудний кандидат (`age > TAU`).
  2. Якщо всі сторінки активні (`age <= TAU`), береться перша неактивна сторінка з `R = 0`.
  3. Якщо всі мають `R = 1`, стрілка скидає їхні біти та обирає перший фрейм за списком (*"беремо першу сторінку за списком"*).
  4. Стрілка завжди коректно просувається вперед за витіснений фрейм.

## 4. Моделювання навантаження та робочого набору

- **Логічний час**: вимірюється виключно в кількості виконаних звернень до пам'яті. Сторінковий промах та повторна спроба вважаються за **одне логічне звернення**.
- **Планування Round-Robin**: квант часу (наприклад, 20 звернень). Процеси отримують процесор по черзі.
- **Робочий набір (WorkingSet)**:
  - 90% звернень спрямовані до сторінок активного робочого набору.
  - 10% звернень — рівномірно випадкові по всьому адресному простору процесу.
  - Кожні `workingSetChangeInterval` звернень процес генерує новий випадковий робочий набір.
- **Справедливість порівняння**:
  - `Simulation.generateWorkload()` попередньо генерує детерміновану трасу звернень та життєвого циклу процесів.
  - Обидва алгоритми тестуються на **абсолютно ідентичній послідовності**!

## 6. Результати експериментів

При запуску `npm run experiment` система автоматично досліджує залежність частоти сторінкових промахів від розміру робочого набору (WS Size) для 40 фізичних фреймів:

```
========================================================================================
PAGE REPLACEMENT COMPARISON: Random vs WSClock across Working Set Sizes
========================================================================================
WS Size   | Total Acc | Random Faults | Random Rate | WSClock Faults | WSClock Rate | Improvement
----------------------------------------------------------------------------------------
4         | 1500      | 148           | 9.87%       | 130            | 8.67%        | -12.2%
8         | 1500      | 241           | 16.07%      | 189            | 12.60%       | -21.6%
12        | 1500      | 413           | 27.53%      | 384            | 25.60%       | -7.0%
16        | 1500      | 574           | 38.27%      | 573            | 38.20%       | -0.2%
20        | 1500      | 683           | 45.53%      | 643            | 42.87%       | -5.9%
24        | 1500      | 776           | 51.73%      | 761            | 50.73%       | -1.9%
========================================================================================
```

### Аналіз та висновки:
1. **Зростання конкуренції за пам'ять**: Зі збільшенням розміру робочого набору з 4 до 24 сторінок сумарна потреба процесів у пам'яті зростає з 12 до 72 сторінок, суттєво перевищуючи фізичний обсяг RAM (40 фреймів). Це спричиняє монотонне зростання частоти сторінкових промахів з ~9% до ~51%.
2. **Перевага WSClock**: Завдяки врахуванню бітів звернення та вікна `TAU`, WSClock утримує активні сторінки і витісняє застарілі, забезпечуючи стабільно нижчу кількість промахів у порівнянні з алгоритмом Random (до 21.6% скорочення кількості page faults).
3. **Неефективність Random**: Випадковий вибір жертви часто витісняє сторінки гарячого робочого набору, що призводить до додаткових перезавантажень з диска.
